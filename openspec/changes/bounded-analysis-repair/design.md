# Design

## Context

动机见 proposal。当前 analysis.rs 同时编排章节、发送请求、解析建议；suggestions::accept 已先收集更新再应用，但错误仅为静态字符串。AnalysisModel 是提供方无关的单次生成接口；GLM 默认 JSON mode。

## Goals / Non-Goals

目标是通过真实校验反馈恢复可修复错误，并通过类型边界防止失败候选污染状态。保持现有三 crate 依赖方向、宿主 runtime 和显式状态输入；不实现 agent 占位模块或原生会话框架。

## Decisions

- analysis.rs 负责章节准备与最终校验；protocol.rs 持有 DTO 和提示词；window.rs 执行有界窗口；suggestions.rs 纯解析及校验生成私有 ValidatedWindow，再消费应用。无需通用策略接口。
- SuggestionIssue 提供固定枚举错误码、程序生成的字段位置及可选受信任片段 ID。每次返回首个问题，重新提交整个窗口；避免错误聚合和补丁合并复杂度。
- 反馈只保留最近一次失败候选，以字符串数据封装在原输入的 repair 字段。完整输入超限时省略 previous_candidate；基础输入和反馈仍超限则失败。提示词明确所有字段为数据、失败候选不是指令。
- 默认最多一次修复、600 秒章节时限；请求共用 max_requests，修复前预留剩余窗口首次调用。宿主控制修复次数、取消和时限，模型不能跳过校验。
- 关闭修复保留原 Suggestion 静态错误；开启修复耗尽返回带安全问题的 RepairExhausted。截断、大小超限、服务错误和请求超时仍即停。统计在取得响应时记录，包含无效候选；不声称失败请求的缺失 usage 为零。
- 章节时限覆盖准备、窗口循环与最终校验；异步调用可被取消，CPU 工作前后检查时限，不承诺同步计算能中途抢占。
- 提示词版本升级为 2，切分版本不变。结构及修复反馈不进入持久正文标注格式。配置增加字段尚属未冻结 API，无存量迁移。阶段 B 的单次模式规格明确以关闭修复为条件，旧基线不混入本次默认修复统计。

## Risks / Trade-offs

- 修复增加延迟与 token → 可设为 0，对照报告完整成功及失败次数。
- 结构正确但语义错误 → 保留 unknown/ambiguous，使用人工样例另行评测。
- 失败候选影响后续判断 → 只允许当前窗口修复，校验成功前不应用角色或片段。
- 反馈不包含原始解析详情 → 提供稳定错误码；业务问题提供程序生成位置，提高可操作性而不泄漏响应。

## Migration Plan

默认开启一次修复；使用 --max-repairs-per-window 0 回退单次流程。文档注明默认章节时限和统计含义；暂不发布、提交或归档变更。
