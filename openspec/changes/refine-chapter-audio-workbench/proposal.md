# Proposal

## Why

章节音频已经能顺序生成、续跑、试听及导出 WAV。当前入口与反馈分散，并且生成统一依赖角色归属分析，让只想听单音色朗读的用户也必须先完成分析。按已确认的 FigCraft 设计收敛单章流程和底部播放器。

## What Changes

- 在同一章节工作台提供「单音色旁白」与「多角色」两种明确的音频制作方式。单音色旁白直接读取整章原文，使用用户明确选择并已就绪的旁白音色。多角色继续走现有章节归属分析、待检查项和声音绑定，通过预检后启动。
- 底部播放区常驻，合并本章音频状态、播放和导出入口。右侧箭头展开胶囊片段轨道或收回到紧凑工具栏。轨道收放与面板、章节切换不改变播放器目标、不重新合成。
- 历史多角色产物继续可用。两种方式生成的任务和音频分别可查、可听，续跑只复用相同冻结输入的任务，停顿和媒体引用继续按任务归属。
- 本次范围为单章。整书音频列表、版本管理、批量生成和整书导出交由工程侧栏的「音频制作」页后续设计。局部音频重做与候选采用继续独立跟踪。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `chapter-audio`：在活动变更 `chapter-audio-generation` 已定义的生成契约上加入两种制作方式、按方式预检和恢复。
- `chapter-audio-editing`：在活动变更 `chapter-audio-workbench` 已定义的音轨和停顿契约上明确紧凑工具栏、轨道收放和任务归属。
- `chapter-production-workspace`：增加单章制作入口、常驻播放区与跨页播放的工作台行为。

## Impact

- UI 依据 [FigCraft 设计稿](../../../docs/design.figcraft)「章节音频 · 制作工作台」页，沿用当前章节路由、角色及待检查入口、共享播放器与 Base UI 组件。
- Rust 宿主的计划、预检、任务查询、导出、SQLite 及 Tauri 绑定需要识别音频制作方式。采用新数据库结构，原库与文件不原地改写。
- `chapter-audio-generation` 和 `chapter-audio-workbench` 提供尚未归档的基线需求。本 change 使用相同能力标识，规格同步按基线、再本变更的顺序进行。旧变更的验证勾选按各自证据管理。
