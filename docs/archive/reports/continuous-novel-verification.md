# 连续真实章节验证

文档前半部分保留 2026-10-06 的历史两轮验证，最新进展见下文“2026-10-09”部分。历史验证检查阶段 D 的运行边界，生产提示词、模型建议协议、Rust API 和接受条件保持不变。不据模型输出改写答案，不提前冻结 v1 或接入 TRNovel。

## 输入与冻结

使用用户已授权的本地《蛊真人》文件，按正文中的章节标题选择前 3 个完整章节，没有拼接不同位置、抽取台词或删除空白。解码使用 UTF-8-SIG；按库既有规则仅将 CRLF / CR 规范化为 LF。冻结后的三章分别为 3387、3139、2498 个 Unicode 标量，正文与导入摘要分别保存。原文件摘要及选取边界保存在私有出处文件。

私有计划、出处、冻结文件、完整快照和导出均留在 `runs/continuous-novel-*` 忽略目录。公开文件只含配置、摘要、计数、时延和固定错误分类，不发布小说正文、人物表或模型响应。原四十例金标和六例小说补充组不改写、不混入本轮；本轮没有完整独立归属金标，不报告语义准确率。

国内 Coding Plan `bigmodel::glm-5.3-flash`，low / JSON，提示词 7、切片版本 1，片段证据模式。保持片段 160 字符、窗口 1000 字符，真实整章使用每窗 24 片段、每章最多 32 请求；每窗最多一次修复，输出 8192 token，请求 / 章节 120 / 600 秒。此前短场景的 8 片段 / 8 请求预算不能覆盖这些完整章节，因此在调用前固定整章预算，不把本轮当作此前短场景准确率对照。

## 验证方式

通用脚本 `scripts/verify-book-run.py` 在第一次调用前复制并冻结计划、二进制摘要、配置与身份观察标签摘要。每章用一个新的 CLI 进程，成功提交后检查既有章节、原有角色及修订历史保持；随后启动 resume 执行下一章。全部完成才测试再次恢复和提交文件摘要不变；失败立即停止该轮，不自动网络重试或切换后端。失败后的 inspect/validate 只检查已提交基础状态，不能被计为章节分析交付。

```powershell
python scripts/verify-book-run.py --binary runs/build-book/debug/castglean.exe --plan runs/continuous-novel-input/plan.json --output runs/my-private-verification --identity-label 方源 --identity-label 古月方源
```

`--output` 必须不存在。模型凭据仍由 CLI 从当前环境或 `.env` 获取，不写入计划。固定错误分类只映射程序已知消息，不回传任意 stderr；未知分类为 process_failed。已提交统计不代表全部花费，失败和中断调用用量保持未知。

身份观察标签在调用前固定。仅检查同一称呼是否持续对应唯一 ID，以及后续章节是否实际以该 ID 提交 resolved 归属；角色仍留在注册表本身不算已经观察到复用。名称匹配仅为诊断，不是独立的一对一金标评分，也不证明台词归属正确。

## 对公开 API 与 v1 的约束

先看完整章节交付率、失败类别、恢复行为及资源用量，再决定下一轮改动。至少需要可靠说明失败阶段和已获得响应的成本，区分完整已提交与局部窗口已接受。验证发现的模型失败不能通过放宽完整覆盖或身份引用校验隐藏。

v1 冻结仍须明确运行格式与正文/标注格式的兼容边界、公开错误与统计的稳定性、恢复时配置漂移规则、最低 Rust 版本和 Linux 实机验证。当前章节级恢复仍允许重复未提交章的远程请求；不承诺精确一次计费或窗口恢复。TRNovel 在这些独立能力验收后集成。

复测第一章保存 344 个完整片段、4 个人物，修订 2；取得 19 次响应，其中 4 次修复，成功提交已知输入 27534、输出 10640 token。整书提交文件为 115323 字节。第二章有限修复后仍缺少目标片段，未提交新修订，第三章未执行。失败后仅有第一章的正式提交，其整书数据与离线导出一致，应用校验通过；首轮的空基础书也通过校验。这验证了失败保留状态，不证明完整计划已交付。

首章只观察到一个匹配既定主角称呼的身份和 9 个 resolved 引用；没有第二章成功产物，所以跨章复用、重复完成恢复和随章增长的存储成本未验收到，语义正确率未测。失败章节已取得响应的统计未由现有 Rust 返回，因此所有调用总数和总成本保持 `null`，不能将 19 次成功提交响应当作全部调用。

公开配置、摘要、执行顺序、计数、统计和边界见 [实测记录](evaluations/continuous-novel-glm.json)。新增验证工具的离线测试覆盖首轮失败、失败恢复不覆盖 checkpoint、超时、无重试、固定错误分类、身份保留不冒充实际复用及完整计划的重复恢复；Python 发现入口已在现有 CI 中。

## 历史验证后的优先级

先补齐安全的失败诊断：返回失败窗口序号、受信任目标引用、已经取得响应的统计与修复耗尽信息；完整章节仍是唯一可发布产物。定位 missing_target 遗漏了什么，再决定是否将确定性的纯空白标注交给程序，或修正完整窗口提交策略。当前没有响应证据证明遗漏只来自空白，因此不据猜测修改分区或删除正文。

这项诊断会影响公共错误和统计边界，应在 v1 冻结前明确，并用失败替身和相同冻结章节复核。继续保持 core 编排与校验、model 通信、CLI 装配和展示的职责，不因此引入 Agent、跨窗口 partial commit 或厂商重试策略。

## 2026-10-09：安全诊断与显式覆盖复测

本轮最多三轮真实调用，均使用原三章完整正文、相同 source hash 和原预算，不改金标或删除空白。每轮独立目录冻结二进制与实际配置，首次失败即停；报告不包含模型响应或私人正文。

第一轮默认提示词 7 / run-1，只新增诊断。首章第 10 个窗口（零起始序号 9）在修复后失败 outside_target：24 个目标，其中 14 个纯空白；第 25 项标注引用无效，未保存无效模型 ID，不能判断它究竟是上下文引用还是捏造引用。接受的 9 个窗口只为私有候选，当前章没有提交。收到 12 个响应、2 个修复响应，已知输入/输出 17227/6385 token；推理用量部分未知。失败空基础书仍通过 inspect/validate。见 [第一轮记录](evaluations/continuous-novel-diagnostics-round1.json)。

第二轮默认提示词 9 / run-2，输入增加 target_ids / target_count，反馈列出全部遗漏短引用；保留失败窗口各次安全校验问题。分区版本、正文、模型配置、窗口/请求/输出/时间预算和每窗修复上限保持不变。三章完整交付，分别独立进程启动/恢复；完成后再次恢复无新提交，原提交文件摘要不变，整书导出校验通过。共收到 40 个成功提交响应。主角称呼匹配候选数为 1/2/2，首章 ID 在三章的 resolved 引用数为 9/15/16；实际复用与候选数量分开报告，没有完整独立金标，不报告语义准确率。见 [第二轮记录](evaluations/continuous-novel-coverage-round2.json)。

本轮报告没有确认纯空白遗漏，因此程序纯空白标注的条件尚未触发；模型继续完整返回全部目标，纯空白数量不能被当作遗漏证据。Unicode 空白、纯空白章与混合正文离线测试验证原文及完整 UTF-8 范围保持。第三轮使用第二轮相同二进制和配置独立复核，不根据姓名合并人物、不增加模型重试。

安全诊断用法见 [模型分析](model-analysis.md#失败诊断草案)。详细统计只说明本次已取得响应，失败或中断调用的未知费用仍不能假定为零；报告不是 checkpoint。阶段 D 的发布冻结、最低 Rust 版本及 Linux 实机验收仍未完成。
